# k3-spherical-twists

Macaulay2 code that checks, on explicit K3 surfaces, numbers that come out of a study of words in two spherical twists, and a small scheduler that runs such checks in batches under time and memory limits.

## What this is about

Let X be a K3 surface with an ample class H, H² = 2d, and put n = d + 2 = h⁰(O(H)). The structure sheaf O and the line bundle O(H) are spherical objects of the derived category of X, and each gives an autoequivalence, the spherical twist T_O or T_{O(H)}. The study behind this repository describes what words in these two twists do to the skyscraper sheaf O_x of a point.

For short words the images are built from a few sheaves that can be written down:

| Sheaf | Definition | Where it occurs |
|---|---|---|
| I_x | ideal sheaf of the point x | T_O(O_x) = I_x[1], T_{O(H)}(O_x) = I_x(H)[1] |
| M_H | kernel of H⁰(O(H)) ⊗ O → O(H) | T_O(O(H)) = M_H[1] |
| M_x | kernel of H⁰(I_x(H)) ⊗ O → I_x(H) | T_O T_{O(H)}(O_x) = M_x[2] |
| Q | cokernel of O → H⁰(O(H))* ⊗ O(H) | T_{O(H)}⁻¹(O) = Q[−1] |

The study predicts the cohomology of these sheaves as formulas in n. This code computes the same numbers on a surface and compares.

## What is computed

`k3Surface d` builds a smooth K3 surface of degree 2d through the point x = (1:0:…:0), over a prime field, as a random complete intersection:

| d | n | Surface |
|---|---|---|
| 2 | 4 | a quartic in P³ |
| 3 | 5 | a quadric and a cubic in P⁴ |
| 4 | 6 | three quadrics in P⁵ |

The surface is determined by d, a seed and a characteristic; the defaults are seed 1 and the prime 32003.

`k3Recipe hashTable {"d" => 2}` validates a recipe before generating equations. The family is `complete_intersection`, with the special quadric available for `d = 3`. `realizeK3Surface` records the actual equations, coordinate order, grading, polarization and marked ideals. The batch decoder accepts an optional `family = "complete_intersection"` and rejects unrecognized surface parameters. The optional seed, characteristic, and special-quadric settings use their defaults when omitted or supplied as JSON null.

The marked lattice of these models is the sublattice generated by the hyperplane class, whose square equals the surface degree. This is the intersection data supplied by the model. Determining the full Picard group requires additional evidence. `markedDivisorLattice` and `divisorClass` can express forms and coordinates of higher rank. `catalogueMukaiClass` returns a parented class for a catalogue sheaf, and `mukaiPairing` and `tensorByDivisor` use its lattice.

`sheafInvariants` returns, for one surface, computed and predicted values of:

| Invariant | Predicted |
|---|---|
| hⁱ(O), hⁱ(O(H)), hⁱ(O(−H)) | (1, 0, 1), (n, 0, 0), (0, 0, n) |
| hⁱ(I_x), hⁱ(I_x(−H)), hⁱ(I_x(H)) | (0, 0, 1), (0, 1, n), (n − 1, 0, 0) |
| rank M_H, hⁱ(M_H), hⁱ(M_H(−H)) | n − 1, (0, 0, n), (0, 1, n² − 1) |
| rank M_x, hⁱ(M_x), hⁱ(M_x(−H)) | n − 2, (0, 0, n − 1), (0, 0, n² − n − 1) |
| rank Q, hⁱ(Q) | n − 1, (n² − 1, 1, 0) |

The numbers n − 1 and n² − n − 1 are the terms c_1, c_2 of the sequence c_0 = 1, c_{k+1} = n·c_k − c_{k−1} (`chainNumber`).

With `Slow => true` some of these are computed a second time as Ext groups, together with Extⁱ(F, F) for F = I_x(H), M_H, M_x (predicted (1, 2, 1), (1, 0, 1), (1, 2, 1)). Those take minutes on the quartic and are not practical for d = 3, 4.

`catalogue` lists the sheaves of the study on a surface with their classes (r, c, s), where c is the multiple of H and the pairing is ⟨v, w⟩ = 2d·cc′ − rs′ − r′s: the line bundles O(tH), the ideal sheaves I_x(tH), O_x, the bundles M_H, M_x, their duals and twists, the bundle E_2 (the kernel of sl(V) ⊗ O → V ⊗ O(H), rank n² − n − 1), and M_2H (the kernel of H⁰(O(2H)) ⊗ O → O(2H)). There are 22 sheaves on each surface. For d = 3 the option `SpecialQuadric => true` takes the quadric x₀x₁ + x₂x₃ + x₄²; `mukaiBundle` is then a rank 2 bundle of class (2, 1, 2) with End = (1, 0, 1), and the catalogue has 26 sheaves.

`extTableRow` computes Extⁱ(E, F) for two sheaves of the catalogue as the cohomology of the sheaf Hom(E, F), using Serre duality when F is the locally free one, and compares the Euler characteristic with −⟨v(E), v(F)⟩. The time grows quickly with the ranks: on the quartic a pair of rank 3 bundles takes about 15 seconds, and a pair of rank 11 bundles does not finish in a quarter of an hour.

### Marked quartics

```macaulay2
needsPackage "K3Twists";
k3Families()
original = k3Surface 2;
lineQuartic = realizeK3Surface k3Recipe hashTable {"family" => "quartic_with_line"};
lineQuartic#"lattice"#"gram"
C = markedCurveSheaf lineQuartic;
cohomologyDims C
extDims(C, C)
saved = markedQuarticSpec lineQuartic;
restored = realizeK3Surface k3Recipe saved;
```

Use `quartic_with_conic` for the conic family. Both families have degree four and use the same seed and characteristic defaults as `k3Surface`. The marked lattice has basis `H,C`, with `H² = 4`, `H·C = deg C`, and `C² = -2`. The `curve` and `point` ideals are in `K#"markedIdeals"`. The point is selected on the curve for the catalogue's point sheaves. Generation uses Macaulay2’s K3Surfaces package and its Cremona dependency. [K3Surfaces documentation](https://macaulay2.com/doc/Macaulay2/share/doc/Macaulay2/K3Surfaces/html/___K3.html)

`markedQuarticSpec` records the equation, curve generators and point generators as sparse integer data, so rebuilding a saved model uses those exact equations and markings. The batch runner accepts the same recipe fields, including the optional `model` table. Distinct explicit markings are part of the inputs that identify a computation.

Run `python3 -m k3batch run batches/marked-quartics.toml` for the curve sheaf's cohomology and self-Ext on both families. The invariant task names are `h^i(O_C)` and `Ext^i(O_C, O_C)`. The original catalogue still uses the hyperplane classes for its entries.

## Apply a word in spherical twists

A word lists its signed steps in application order. A sign of 1 applies a twist and -1 applies its inverse.

```macaulay2
K = k3Surface 2;
P = catalogueObject(K, "O_x");
S = sphericalObject structureObject K;
T = sphericalObject lineBundleObject(K, K#"polarization");
W = twistWord {twistStep(S, 1), twistStep(T, -1)};
E = applyWord(W, P, VerifiedOnly => true)
v = mukaiClass E;
{v#"rank", (v#"divisor")#"coordinates", v#"eulerComponent"}
```

This gives the symbolic image of the point sheaf and its Mukai coordinates `{2, {3}, 9}`. Symbolic images share prefixes on the same realized model and retain each generator's evidence. The structure and line bundle generators use the K3 line bundle theorem. `checkedSphericalObject` checks a catalogue sheaf through self-Ext, while `assumeSphericalObject` records an explicit hypothesis and is excluded by `VerifiedOnly`.

Use `applyWordToClass` to evaluate a long word using only integer lattice arithmetic. `shiftObject` records a cohomological shift, so even shifts can give distinct objects with equal Mukai classes. Realizing the symbolic image as a complex is a separate operation.

## Requirements

Macaulay2 (version 1.25 was used) and Python 3.11 or later; the scheduler uses the standard library only. Linux is assumed: the scheduler reads `/proc` and, where `systemd-run --user` is available, uses control groups.

Without a system install, build the container once and run inside it:

```bash
docker build -t k3-twists-m2 .
```

```bash
docker run --rm -v "$PWD":/work -w /work k3-twists-m2 make test
```

## Running a batch

A long computation is described as a batch: a file that says which surfaces, which tasks, which limits, and how much of the machine to use. One task is one computation with one answer, for example Extⁱ(M_H, M_x) on the quartic with seed 1 over the field with 32003 elements.

```bash
python3 -m k3batch plan batches/quartic-sample.toml
```

```bash
python3 -m k3batch run batches/quartic-sample.toml
```

```bash
python3 -m k3batch report results/quartic-sample
```

`plan` lists the tasks a run would compute, with their costs and limits, and computes nothing. `run` computes each task that lacks a reusable record for its exact computation. `report` prints tables from the records. `make plan`, `make run` and `make report` do the same with `BATCH=batches/….toml`.

### The batch file

```toml
name = "example"                 # results go to results/example

[scheduler]
workers = 4                      # task processes at a time
memory_budget_mb = 4000          # the memory limits of running tasks never add up to more

[limits]                         # limits of one task
time_seconds = 300
memory_mb = 1000

[[limits.tier]]                  # tasks of cost 9 or more get other limits
min_cost = 9
time_seconds = 3600
memory_mb = 3000

[[surfaces]]
d = 2                            # also: seed, characteristic, special_quadric

[[tasks]]
kind = "ext_pair"
sheaves = ["O", "O(1H)", "M_H", "M_x", "O_x"]
```

Every `[[tasks]]` table is expanded on every surface. The kinds are:

| Kind | Tasks | Keys |
|---|---|---|
| `ext_pair` | Extⁱ(E, F) for each ordered pair | `sheaves = "all"` or a list of names; or `sources` and `targets` |
| `invariant` | one entry of `sheafInvariants` | `names = "fast"`, `"slow"`, `"all"` or a list of names |
| `synthetic` | no mathematics: sleeps, holds memory or fails | `items`, each with `name` and `sleep_seconds`, `allocate_mb`, `fail` |

A `[[tasks]]` table may carry its own `limits = { time_seconds = …, memory_mb = … }`. A task gets the limits of its table if there are any, otherwise those of the highest tier whose `min_cost` it reaches, otherwise the defaults. On the command line `--workers`, `--memory-budget`, `--time-limit` and `--memory-limit` replace the scheduler settings and the default limits.

Each task has a cost. For a pair it is the rank of the sheaf Hom(E, F). The cost is a hint and not an estimate of the time: tasks run in order of cost, cheapest first, and tiers use it to give expensive tasks larger limits. Tasks whose memory limits do not fit the budget together never run at the same time; a task whose limit is the whole budget runs alone.

The batches in `batches/`:

| File | Content |
|---|---|
| `quartic-sample.toml` | 25 pairs among five sheaves on the quartic; half a minute |
| `marked-quartics.toml` | Cohomology and self-Ext of a marked line and conic |
| `invariants.toml` | the fast invariants for d = 2, 3, 4; seconds |
| `invariants-slow.toml` | the slow invariants on the quartic; minutes |
| `ext-table.toml` | every pair of the catalogue on four surfaces, 2128 tasks; many hours, and the largest pairs will reach their limits |
| `limits-demo.toml` | six pairs and two synthetic tasks that are stopped at a time limit and at a memory limit |

### What a run guarantees

- **One runner per task.** Each task runs in its own Macaulay2 process and writes a separate result record.
- **Limits are enforced from outside.** A watchdog owns each job tree, including planning jobs, and checks its wall deadline independently of scheduler logging and record writes. The planner has a 600-second limit and uses the run's memory budget. A task starts when a worker slot and enough memory budget are available.
- **Run and job memory budgets.** With `--memory-guard cgroup`, a transient cgroup v2 slice caps total runner memory and CPU across the run. Each job has its own memory cap and runtime limit under the run slice. Both slices disable swap. The run CPU quota defaults to the number of worker slots, and a single job may use available cores under that quota.
- **Coordinator headroom.** The initial memory check accounts for the run budget plus 64 MiB for the coordinator and 16 MiB per worker watchdog. These allowances are estimates outside the runner slice. Concurrent runs have separate limits and share the host's available memory. `--overcommit` opts out of the initial memory preflight.
- **One record per finished attempt.** With the default JSONL store the scheduler appends and syncs each result before counting it as recorded. Reports count unreadable lines. The next writer starts on a new line after any interrupted write. With the SQLite store the result and the attempt’s terminal state commit in one transaction.
- **Exact resumption.** A rerun can reuse the latest record with the same computation fingerprint. Labels identify tasks in a report. Changing the operation, inputs, implementation or runtime fingerprint causes recomputation. Increasing the relevant limit retries a timeout or memory stop. `--retry timeout,memory` explicitly retries those statuses. A task without a completed record after interruption stays eligible to run.
- **Job cleanup.** The watchdog cancels and reaps its job on coordinator death or interruption. The cgroup backend also has systemd scope deadlines. Two runs cannot write to the same results.

The default `--memory-guard auto` uses cgroup v2 when the systemd user manager can enforce the required controllers. Explicit `--memory-guard cgroup` requires those controllers. `--memory-guard poll` samples the job's process tree RSS and has no kernel memory, swap, or CPU quota. Samples can overshoot and can count shared pages more than once.

Runner jobs have a 16 MiB per-file limit, including standard output and error directed to regular files. A job's private temporary directory is checked periodically against a 128 MiB budget for allocated blocks and directory entries. Output and scratch limits are per job. The run's retained logs are cumulative. Planning and task deadlines apply independently, and temporary resource bookkeeping is removed when the watchdog can complete cleanup. A coordinator killed during slice creation can leave an empty transient unit.

### Records

A record carries the task, its outcome and where it came from:

```json
{"task_id": "ext_pair/d2-p32003-s1/M_H/M_x",
 "schema_version": 1, "computation_id": "…", "check_id": "…", "record_id": "…",
 "task": {"kind": "ext_pair", "source": "M_H", "target": "M_x", "cost": 6,
          "surface": {"d": 2, "seed": 1, "characteristic": 32003, "special_quadric": false}, "…": "…"},
 "status": "ok",
 "value": {"dims": [0, 0, 1], "chi": 1}, "predicted": {"chi": 1}, "agrees": true,
 "detail": {"method": "Serre duality", "setup_seconds": 0.006, "compute_seconds": 2.1},
 "wall_seconds": 2.6, "cpu_seconds": 3.9, "peak_rss_mb": 325.6,
 "limits": {"time_seconds": 300, "memory_mb": 1000}, "memory_guard": "cgroup",
 "exit_code": 0, "exit_signal": null, "error": null, "log": null,
 "started_at": "…", "run_id": "…", "attempt_id": "…",
 "runner": {"m2_version": "1.25.11", "package": "K3Twists 0.2"},
 "code": {"commit": "…", "dirty": false}}
```

| Status | Meaning |
|---|---|
| `ok` | a value was computed; it agrees with the predicted value, or there is none |
| `mismatch` | a value was computed and differs from the predicted value |
| `unsupported` | there is no method for the task (a pair of two sheaves that are not locally free) |
| `timeout` | stopped at the time limit |
| `memory` | stopped at the memory limit |
| `error` | Macaulay2 reported an error; the message is in the record |
| `crashed` | the process ended without a result for another reason |

`peak_rss_mb` is the largest resident size of the task's process, as the kernel reports it when the process ends. The watchdog measures `wall_seconds` through process exit. If the watchdog dies before reporting, the coordinator measures through collection. Records also include the requested and effective resource controls. In cgroup mode they include the cgroup memory peak and memory events. A signal alone is not evidence of a local memory kill. In polling mode the recorded RSS sample is separate from the leader's kernel RSS high-water mark. The output of an attempt that times out, exceeds its memory limit, errors or crashes is kept in `results/<name>/logs/`. Each attempt uses a distinct log filename so its record continues to point to the original output after a retry. Next to the records, `runs.jsonl` has one line per run with the configuration as it was resolved, the command line, the versions and the memory available at the start, and `manifest.json` lists the tasks of the latest run with their limits.

`run` exits with status 0 when every task of the batch is `ok` or `unsupported`, 1 when a task is `mismatch`, `error` or `crashed`, 3 when nothing failed but tasks were stopped at a limit, and 2 when the batch cannot be run as asked.

### Committed records

A run writes to `results/<batch>/`, which is not in git. The records behind [CLAIMS.md](CLAIMS.md) are in [records/](records/), one directory per batch:

```bash
make record BATCH=batches/invariants.toml
```

```bash
make tables
```

`make record` runs the batch and copies its records to `records/<batch>/`; for `batches/limits-demo.toml`, whose synthetic tasks are stopped on purpose, add `EXPECT=3`. `make adopt BATCHES="a b"` copies the records of runs that are already in `results/`. For a batch with a `[graph]` table, `make plan`, `make run` and `make record` use the SQLite store at `results/<batch>/results.sqlite`, and the records are adopted from it. A record is copied only if it was computed from committed code with no uncommitted change in the working tree (an untracked file counts as one), and only if it names neither the machine nor a directory outside the repository; [tools/adopt.py](tools/adopt.py) has the rules. `make tables` then rewrites the generated tables, and `make check` fails when they are not what the registry, the batch files and the records give.

In the tables a record counts for a task as long as the task is the same computation with the same predicted value, whatever has changed in the code since; the record names its commit. A record of a task that has changed reads `stale`. This is a rule of the tables only. When the scheduler decides whether to compute a task again it also compares the code, as described under [Reports](#reports).

### Reports

With JSONL storage, the scheduler saves a separate manifest under `runs/<id>.json` before each run starts. It pins the exact result record selected for each task and carries a revised check when a runner declares that the observation supports independent comparison.

`report` defaults to the latest run. Use `python3 -m k3batch report results/quartic-sample --run <id>` to select an earlier run using its printed ID or its ID in `runs.jsonl`. Reports from before run manifests were introduced remain readable. Use `--legacy` to read unversioned historical records from a directory that also has versioned runs. Unversioned records are ineligible for automatic reuse.

Computation fingerprints include the expanded operation and scientific inputs, local package source contents, runner versions, and the launcher and recognized runner script contents. Placement fields (`id`, `set`, `group`, and `cost`) describe the report and schedule. At the start of each plan or run, the CLI copies the package, scheduler, and repository-local runner files that contribute to the fingerprint into a private source directory. Expansion and tasks run from that directory, so edits and commits made after capture are picked up by the next run. A dirty checkout contributes its captured file contents and is recorded with `code.dirty: true`. Custom runners should use absolute paths for data outside the snapshot and include their external code and runtime versions in their expansion metadata.

A runner may declare `comparison = "equals"` for full-value comparison or `comparison = "fields"` for comparing named fields of an object. This declaration promises that the prediction and comparison mode leave the calculated observation unchanged. The scheduler can then check a changed prediction against the earlier observation while retaining both checks in their respective run manifests. Changes to hashed source files still invalidate the implementation fingerprint.

`report` prints, as Markdown: a summary by group and status, the computed values that differ from the predicted ones, the tasks stopped at a limit with their limits, wall time and peak memory, the errors, and the pairs with no method. `--full` lists every computed value against its predicted value. For the sample batch:

```
| group | tasks | ok | unsupported |
|---|---|---|---|
| ext_pair d2-p32003-s1 | 25 | 24 | 1 |
```

### SQLite results

Use `--store` with a local SQLite path to keep several batch runs in one database. Their output directories still hold logs and runner files. The database records run membership, attempts and their outcomes, prediction revisions, and artifact descriptors supplied by the runner. Exact matches can be reused across output directories. Reports resolve logs relative to the directory of the original attempt.

```bash
python3 -m k3batch plan batches/quartic-sample.toml --store results/study.sqlite
python3 -m k3batch run batches/quartic-sample.toml --store results/study.sqlite
python3 -m k3batch report results/quartic-sample --store results/study.sqlite --run RUN_ID --full
```

A database admits one writing coordinator at a time. Readers can inspect committed results while a run is active. If the coordinator dies, the next writer marks its running attempts and run as interrupted. Completed records remain available. The database uses WAL mode on local storage.

Import from a completed JSONL run directory to retain the original records, available manifests, and run metadata. A repeated import skips records that are already present. Unversioned records stay available for historical reports. The source files are left in place.

```bash
python3 -m k3batch import-jsonl results/earlier-experiment --store results/study.sqlite
python3 -m k3batch report results/earlier-experiment --store results/study.sqlite --legacy
python3 -m k3batch export-jsonl --store results/study.sqlite --run RUN_ID > pinned-results.jsonl
```

Without `--run`, export writes one standalone JSON row per finished attempt. Use `--surface '{"d":2,"seed":1,"characteristic":32003,"special_quadric":false}'` to match a complete surface object, or filter with `--method`, `--observation` for a result record ID, or `--commit`. With `--run`, export includes the exact observations and checks the run pinned, with the source record ID, source run ID, and selected run ID. The run report shows tasks without a result as “not run.”

Use `export-run` to copy a pinned SQLite run and its registered mathematical
artifacts to a new directory. The bundle contains the selected manifest and
records, file digests, and content-addressed artifact files. Chain maps bring
both complex endpoints and their model with them.

```bash
python3 -m k3batch export-run results/quartic-sample exported-run --store results/study.sqlite --run RUN_ID
```

### Marked quintic threefold

The same object and signed-word API can run on a smooth Fermat quintic over
`ZZ/101`, marked at `(1:-1:0:0:0)`. The constructor checks the Jacobian and
point ideal. Adjunction gives the trivial canonical bundle and Serre shift 3.
Use `varietyEvidence`, `varietyCapabilities`, and `distinguishedObjects` on
either model to inspect the available operations.

```m2
Y = quinticThreefold()
Oref = structureObject Y
P = catalogueObject(Y, "O_x")
cohomologyObservation Oref
extObservation(P, Oref)
W = twistWord {twistStep(sphericalObject Oref, 1)}
A = realizeTwistImage applyWord(W, P, VerifiedOnly => true)
numericalClass A
realizedHomology(A, -1)
```

The structure sheaf has dimensions `(1,0,0,1)`. On the numerical subgroup
spanned by the structure and point sheaves, the two Euler pairings are 1 and
−1 respectively. The forward word subtracts `[O]` from `[O_x]`, and its native
evaluation cone realizes `I_x[1]`. The inverse uses the opposite numerical
transvection. Explicit realization on this model is scoped to the single
certified forward structure twist of the marked point.

### Certified quartic cones

In addition to evaluation of the marked point sheaf and the hyperplane bundle
by `O`, the realization backend supports the inverse twist of `O` about
`L = O(H)` on a smooth quartic. The four coordinate sections are a basis of
`Hom(O,L)`. The higher groups vanish by the cohomology of the hyperplane
bundle, so this basis and its dual give a finite derived coevaluation model.
The column of coordinates represents `O → L^4`. Its cokernel is the
independently constructed `quotientBundle K`, and its shifted cone is
`Q[-1]`. Applying the forward twist to this representative uses the quotient
map `L^4 → Q`. Twisting the exact sequence by `-H` and applying Serre duality
shows that this quotient map uses all of `Hom(L,Q)` and the higher groups
vanish. The two maps compose to zero and identify the kernel with `O`,
which verifies the forward and inverse cancellation.
[Seidel and Thomas, Definition 2.7 and Proposition 2.10](https://arxiv.org/abs/math/0001043)

The forward twist `T_O(O(-H))` uses the four-dimensional degree-two Ext
group. The resolution of an ideal defining the affine cone vertex gives a
finite model of `O[-2]`. Graded local duality identifies its Ext classes
with sheaf cohomology in the two internal degrees used here. Multiplication by
the four coordinates gives the Serre pairing in a chosen trace basis. The
evaluation uses the dual basis and the realization records its chain map,
Ext dimensions, and pairing matrix. The cone has sheaf homology `O(-H)`
in cohomological degree zero and `O^4` in degree one, giving Mukai class
`(-3,-H,-1)`.

For the signed word `{T_O, T_O^-1}` acting on `O(-H)`, call
`realizeTwistImage(W, E)` with the word and starting object. It retains each
step and builds the inverse coevaluation from the projection of the forward
cone, followed by the augmentation to `O^4[-1]`. The dual-section rank of
the projection is four, which verifies the four Serre functionals on
degree-three hypercohomology. The resulting comparison from `O(-H)` to the
shifted inverse cone is a quasi-isomorphism after sheafification.

The mixed word `{T_O, T_{O(H)}^-1}` on `O_x` uses the comparison from
`I_x[1]` to the point evaluation cone. The coevaluation on a finite model
of the point ideal uses four coordinate sections in degree zero and a
nonzero Ext class in degree one. Explicit homology maps identify the
mixed cone's sheaf homology with `O(H)` in degree −1 and
`coker(I_x → O(H)^4)` in degree 0. Its Mukai class is `(2,3H,9)`.

For a certified line bundle `S = O` or `O(H)`, `RHom(S,S)` is
`RΓ(O)` with one-dimensional cohomology in degrees 0 and 2. Splitting
a complex of vector spaces over the coefficient field gives summands
`k` and `k[-2]`. Choose the identity as the degree-zero lift and a class
with nonzero Serre trace in degree two. The derived evaluation on
`S ⊕ S[-2]` has identity as its first component. A triangular change of
basis eliminates the other component, leaving `S[-1]` after the identity
cone contracts. Dually, coevaluation takes values in `S ⊕ S[2]` and its
shifted cone leaves `S[1]`. The resulting one-term complexes and the
comparison apply to shifts of the same generator and to repeated signed
steps on it. Other higher-degree evaluations and mixed words
still require explicit derived Hom models.

Macaulay2 indexes the complexes homologically. Homological degree `j`
corresponds to cohomological degree `-j`, and moving the two-term
differential by an odd shift changes its sign. Use `realizedHomology`
with the cohomological degree to inspect the associated sheaf.

In one Ubuntu run with Macaulay2 1.25.11, `T_O(T_O(O))` realized `O[-2]`
in 0.053 s after the quartic was available. The complete process took
5.06 s and peaked at 164.8 MiB RSS, including startup and surface construction.

## Mathematical artifacts

Macaulay2 functions encode a K3 model, a graded module presentation, or a bounded
complex of finitely presented modules as versioned data. The data preserves the
equations, markings, basis degrees, module relations, and differentials. Complex
degrees are homological. Free complexes use version 1. A complex with a presented
term uses version 2 and records a graded presentation for each term. The
Macaulay2 loader reads both versions and checks the parent model, internal
grading, compatibility of each differential with the module relations, and
composition of consecutive differentials.

To save a model from Macaulay2, load `JSON` and write
`"model.json" << toJSON k3ModelArtifact K << close`. Publish the JSON to get the
digest, then fetch its verified bytes for another process.

```bash
model=$(python3 -m k3batch publish-artifact results/artifacts model.json --producer attempt-1)
python3 -m k3batch read-artifact results/artifacts "$model" > verified-model.json
```

Use `loadK3ModelArtifact(fromJSON get "verified-model.json", digest)` in the new
process with the returned digest. To save an object already computed on `K`, use
`bindK3ModelArtifact(K, fromJSON get "verified-model.json", digest)` to identify its
existing model. Use `gradedPresentationArtifact` or `gradedComplexArtifact` to encode
a dependent object and publish it with the same command. The store verifies the
registered model before publishing or reading dependents. The M2 functions
`loadGradedPresentation` and `loadGradedComplex` take that loaded model and the
verified dependent data.

The store records SHA-256, schema version, kind, byte size, parent model and producer
IDs. Publication flushes the staged file, links it to its digest path, then registers
it in SQLite. A stage left by a crash is ignored and can be removed after writers stop.
A file linked before registration is unavailable to readers until identical bytes are
published again. Two attempts publishing identical bytes share one object and keep
both producer IDs. A digest mismatch is an error on read and on repeated publication.

On Ubuntu with Macaulay2 1.25.11, the degree-eight complete intersection
(`d = 4`, seed 1) used 1,685 bytes for the model and 12,559 bytes for the rank-five
hyperplane kernel bundle's 18-by-38 presentation. Encoding the model and presentation
took about 0.007 s and 0.08 s, respectively. A fresh process took 0.39 s to validate
and reload the model and 4.03 s to reload the presentation and form the sheaf.
These timings exclude M2 startup, publication, and initial bundle construction.

### Dependent batches

A batch can include a versioned `[graph]` table. Node IDs refer to the task IDs
printed by `k3batch plan`. Tasks without graph declarations remain independent.

```toml
[graph]
version = 1

[[graph.nodes]]
id = "make-model"
outputs = { model = "k3-model" }

[[graph.nodes]]
id = "make-prefix"
outputs = { cone = "graded-complex" }
inputs.surface = { producer = "make-model", output = "model", kind = "k3-model" }

[[graph.nodes]]
id = "measure-prefix"
[graph.nodes.inputs.surface]
producer = "make-model"
output = "model"
kind = "k3-model"
[graph.nodes.inputs.prefix]
producer = "make-prefix"
output = "cone"
kind = "graded-complex"
model_input = "surface"
```

Use `--store DATABASE` for a graph. Artifacts live in the sibling directory
`DATABASE.artifacts`. A runner receives verified inputs by name in `inputs`, with
the artifact data, digest and source attempt. Return exact artifact envelopes by
name in the result's `artifacts` field. Supported output kinds are `k3-model`,
`graded-presentation` and `graded-complex`. A dependent mathematical artifact
requires its model to be registered. Use an upstream model node to obtain the
model digest for a new complex or presentation.

The coordinator validates graph topology and contracts before admitting tasks.
It verifies the content of an input and any declared `model_input` relationship
before starting a consumer. Each new claim is recorded in SQLite, and a producer's
artifacts are published before its successful attempt is committed. Descendants
of a failed prerequisite record its cause as `blocked`. Independent work can finish.

On resume, a successful linked attempt can supply its artifacts again. If a
process dies between artifact publication and the attempt commit, the next run
repeats that attempt and identical bytes share the existing artifact. Consumer
records pin the upstream record IDs, so retrying a producer selects new work for
its consumers. Runs with no graph edges follow the usual scheduling and reuse rules.

### Resumable marked quartic study

At the Macaulay2 prompt, load the package and evaluate the expressions in
`examples/resumable-quartic.m2`. From the repository root the same session runs
with `M2 --script examples/resumable-quartic.m2`. The line marking gives
the ordered basis `H, C` with Gram matrix `{{4,1},{1,-2}}`. The script shows
the catalogue, the class `(-3,(1,0),-1)` of the forward twist of `O(H)` about
`O`, its realization as `M_H[1]`, and the capability response for the
inverse twist about `O` on `O(H)`.

The batch uses the same marked quartic over `ZZ/32003` with seed 1,
input line bundle and signed word. Run through the cone checkpoint with
enforced cgroup v2 limits, then resume against the same ledger.

```bash
scratch=$(mktemp -d)
python3 -m k3batch run batches/resumable-quartic.toml \
    --store "$scratch/study.sqlite" --out "$scratch/run" \
    --memory-guard cgroup --checkpoint-after quartic_prefix/realize
python3 -m k3batch run batches/resumable-quartic.toml \
    --store "$scratch/study.sqlite" --out "$scratch/run" --memory-guard cgroup
python3 -m k3batch report "$scratch/run" \
    --store "$scratch/study.sqlite" --run RUN_ID --full
```

The checkpoint returns status 130 after the cone and its attempt have been
committed. On resume, the model and cone are reused and the two observations
each reload their verified inputs in a fresh process. Substitute the printed
ID of the resumed run for `RUN_ID`. The pinned report records the degrees
and dimensions, hypotheses and prediction versions, artifact digests, source
attempt IDs, and memory-control mode. The cohomology table is `(0,0,4)` in
degrees −1 through 1, and Ext from the realized object to `O` is `(4,0,0)`
in degrees 1 through 3.

Use `batches/marked-quartics.toml` for cohomology and self-Ext of the marked
line and conic as curves on their respective quartics.

Use `batches/resumable-quartic-point.toml` with the same checkpoint and report
commands and a fresh ledger to study the marked point. Its realization selects
`target = "O_x"` and publishes a version 2 cone because the point sheaf has a
presented module term. The cohomology of `I_x[1]` is `(0,0,1)` in degrees −1
through 1, and Ext to `O` is `(1,0,0)` in degrees 1 through 3.

Use `batches/resumable-quartic-mixed-point.toml` to resume the mixed word
from that same version 2 checkpoint. The inverse worker checks the comparison
to `I_x[1]` and publishes the mixed cone, the coevaluation, and the
comparison from its finite source back to the saved cone.

Use `batches/resumable-quartic-hypercohomology.toml` to observe the entire
reloaded `T_O(O(-H))` cone. The batch computes derived global sections using
the differentials and compares the hypercohomology with the evaluation triangle.
Only degree 3 is nonzero, of dimension four. From M2, use
`hypercohomologyObservation(K, C)` on a graded complex over the quartic model
`K`. The observed degrees are cohomological.

Use `batches/resumable-quartic-inverse.toml` with the same checkpoint and
report commands and a fresh SQLite ledger. The forward task writes the cone,
evaluation, and source augmentation together. After the checkpoint, the
hypercohomology worker reads the saved cone and the inverse worker checks the
saved maps against that same cone. The pinned report gives both workers' input
digests and source attempt, the degree-three hypercohomology, and the verified
sheaf quasi-isomorphism with `O(-H)`.

Use `batches/resumable-quartic-second-forward.toml` to run a third consumer of
that saved forward prefix. It computes the second forward twist from the
reloaded evaluation triangle and publishes the second cone, evaluation, and
source augmentation. The pinned report records one shared forward attempt,
the restored Mukai class, and sheaf homology `O(-H)`, `O^4`, and `O^4` in
cohomological degrees 0, 1, and 2.

### Resource history and bounded retries

Add a `[resources]` table to opt in to history-based admission. The usual
batch limits and tiers supply the initial request. For example:

```toml
[resources]
minimum_samples = 3
retry_attempts = 2
memory_ceiling_mb = 1000
time_ceiling_seconds = 300
cpu_ceiling = 2
```

The estimator uses up to twelve recent results for the same computation,
including its implementation and dependency records. It groups by runner method,
backend and measurement type. A cgroup memory peak and a sampled process-tree
peak are separate signals. Successful jobs contribute observed memory, wall time
and CPU time. A memory or time limit supplies a censored lower bound once enough
comparable successes are available. Estimates include headroom and fit within
the configured ceilings and the run's budgets. `plan` shows the initial request
and its basis. Use `--retry ok` to collect new measurements for an already cached
successful computation.

A confirmed memory limit or an external deadline can trigger a larger reservation,
up to the corresponding ceiling. A retry comes back through normal CPU and
memory admission. The logical result and any graph dependants settle after the
final trial. The result records each trial's request, effective controls and
decision. An interrupted logical attempt is eligible for a fresh run. Use
`--resource-retries N` to override the maximum number of automatic retries.

### Run-wide execution limits

Set `--run-time-limit SECONDS` or `scheduler.run_time_seconds` for one wall
deadline shared by planning and every job. Job watchdogs receive the remaining
time as an absolute deadline and enforce it independently of the coordinator.
If the deadline expires, the CLI returns exit status 3. A SQLite run is marked
interrupted, and a subsequent run can reuse the attempts committed before the
deadline.

`--cpu-budget CORES` or `scheduler.cpu_budget_cores` sets the run's CPU budget.
Use `cpu_cores` in the defaults, a cost tier or a task set's limits to reserve
a weighted share. With explicit CPU settings, an unspecified job reserves one
core. Both worker slots and CPU reservations govern admission. The cgroup
backend enforces the run and job quotas. Sampled mode uses the same admission
budget and continues to report sampled enforcement.

For a hard capacity on the transient workspace, set `scheduler.scratch_root`
to a directory on a size-limited tmpfs mount and set `scheduler.scratch_budget_mb`
to the largest acceptable mount capacity. The equivalent flags are
`--scratch-root PATH` and `--scratch-budget MB`. The backend verifies the mount
type and capacity before using it for planner I/O, runner request and response
files, and job scratch space. Runs sharing one mount compete for its aggregate
capacity. Use a dedicated mount for isolated scratch capacity. Durable result
databases, artifact stores and retained logs use their configured output paths.
The file size limit still applies to each job log.

## Design

Macaulay2 does the mathematics and nothing else. `runTask` computes one task and `expandBatch` lists the tasks of a batch, including which pairs exist and what they cost; `runners/task-runner.m2` exposes the two as a command that reads and prints JSON. The scheduler is in Python and knows no mathematics: it calls the runner, enforces limits and keeps records. It is tested against a fake runner without Macaulay2.

The process boundary is the task because Macaulay2 cannot be relied on to stop itself or to isolate work inside one process:

- `alarm` interrupts interpreted loops, Gröbner bases, resolutions and Hom sheaves within a fraction of a second of the set time, but a global `Ext` of sheaves on the degree 6 surface ran for seven minutes past a five second alarm without being interrupted.
- Macaulay2's tasks (`schedule`, `parallelApply`) are threads of one process. They share its memory, a single one cannot be killed, and `cancelTask` sets the same interrupt flag as `alarm`.
- A process that serves several tasks carries state from one to the next: sheaves cache what was computed with them, so the time and memory of a task would depend on which tasks ran before it.

A process per task costs the start of Macaulay2 and the loading of the package, 0.4 seconds, plus the construction of the two sheaves of the task. The catalogue builds each sheaf on request for that reason: building all of it takes 0.02 seconds on the quartic, 4.6 seconds for d = 3 and 1.1 seconds for d = 4, almost all of it for the duals of M_H and M_x.

### Runner protocol

The bundled Macaulay2 runner uses separate request and response files. Python invokes
`M2 --script runners/task-runner.m2 protocol-v2 REQUEST RESPONSE` and keeps process
diagnostics in the usual task log. A request is one UTF-8 JSON object with `version`
(2), `operation_version` (1), `request_id`, `operation` (`expand` or `run`), and
`payload`. The payload is a batch description for expansion and one expanded task
for execution. The response echoes the request fields except its payload and adds
`type`, `payload`, and `outputs`.

| Response type | Payload |
| --- | --- |
| `expansion` | `tasks`, `count`, and `versions` |
| `result` | `status`, `value`, `predicted`, `agrees`, `method`, and timing |
| `failure` | `code` and `message`. Detailed diagnostics are on the process output. |

Task kinds register their own input and result checks along with an expansion
function, computation function, kind version, and requirement names. Planning uses
catalogue and prediction metadata from the surface parameters. Each task constructs
and validates its surface when it runs. A kind may provide output descriptors with
`name`, `media_type`, and `digest`. These descriptors travel with the result
record. The dependency scheduler publishes and resolves artifacts for declared graph nodes.

Custom shell runners use the legacy `expand` and `run` commands with argv JSON
and marker lines. A custom runner whose command ends in `protocol-v2` is given the
request and response files instead, as the bundled one is. The bundled M2 entry point
also accepts the legacy modes for direct use and for compatibility with older drivers.

## Tests

```bash
make test
```

```bash
make test-slow
```

`make test` runs the fast tests of the package (every test that is not slow, about twenty seconds; the test runner prints how many) and the tests of the scheduler (about two minutes; they include real Macaulay2 tasks stopped at a time limit and at a memory limit). `make test-slow` runs the slow package tests, which compute Ext groups and take under two minutes together; a test is slow when its first line is `-- slow`. `make test-all` runs both. In Macaulay2, `check "K3Twists"` runs every test of the package.

`make check` expands every batch file with Macaulay2 and fails if the claim registry does not fit the tasks or if a generated table is out of date. `make smoke` is described under [Claims and records](#claims-and-records).

`make lint` runs `ruff` and `mypy` on the scheduler and the tools; neither is needed to run them. There is no linter or formatter for the Macaulay2 language; `installPackage "K3Twists"` checks that every exported function is documented and that the examples run.

## What this does not show

- It computes sheaf cohomology. It does not test Bridgeland stability, which is what most of the study's statements are about.
- The surfaces are over finite fields and their Picard rank is not determined. The numbers checked here do not depend on the Picard rank.
- Only the sheaves above are covered, which correspond to words of length at most two. Images of longer words are complexes, and building them is the next thing to add.
- The predicted values follow from short exact sequences; agreement confirms those computations and the code, not the theory as a whole.
- For a pair of sheaves only the Euler characteristic is predicted; the three dimensions are computed and recorded but compared with nothing.
